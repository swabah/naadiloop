# ISSUE-009 — Report Review & Loop Closure (Human Gate #2)

**Blocked by:** 008 (Provider Dashboard & Care-Gap Detection)
**PRD refs:** §5, §6.5 (US-12/US-13/US-14), §7.1, §8.2–8.3, §10.1, §18

## Why

Completion is not loop closure for an action that requires review. A Provider must explicitly review the returned result, communicate the next step, and optionally create a follow-up before the original Care action can close.

## Scope

### Backend / Logic scope

- Implement `provider.reviewReport` and `provider.createFollowUp`.
- Add a single, testable state-transition/closure policy used by every closing procedure.
- On review, update Report and Care action state and write review events atomically.
- Allow an optional Provider comment and optional FOLLOW_UP action linked to the same Care plan.
- Record next-step communication explicitly, either with a dedicated field/event or another schema representation that can be queried and tested.
- Permit `CLOSED` only when the action is completed, reviewed when `reviewRequired`, and the next step has been communicated.
- Write follow-up-created and closed events in the same transaction as their state changes.

### Frontend / UI scope

- Replace the Provider report-review placeholder with report context, file link/preview, optional comment, explicit Review control, and optional follow-up form.
- Reserve the `gate` color for this second human-gate moment.
- Show the resulting state on the dashboard.
- Allow Patient polling to reveal the communicated next step or newly created follow-up.

## Acceptance Criteria

- [ ] Only reports in an awaiting-review state can be reviewed.
- [ ] Reviewing updates both Report and Care action state and writes review events atomically.
- [ ] Provider comment remains optional.
- [ ] A Provider can optionally create a valid FOLLOW_UP action.
- [ ] Follow-up creation writes its own Action event.
- [ ] A review-bearing action cannot reach `CLOSED` before completion, review, and next-step communication.
- [ ] A non-review action follows the same closure policy with the review condition omitted.
- [ ] Closure writes a `CLOSED` event atomically.
- [ ] Transition tests prove invalid shortcuts to `CLOSED` are rejected.
- [ ] After review, the Patient sees the updated next action on the next poll.
- [ ] The demo comment and cardiology follow-up path work without developer intervention.

## Risks / Open Questions

- The scaffold does not yet model “next step communicated” explicitly. The implementation plan must settle that interface before code changes.
- A follow-up should not silently imply medical advice generated by AI; it is Provider-authored.
